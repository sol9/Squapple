## 문서 사용법

각 단계의 작업을 수행한 뒤 체크한다. 단계 마지막의 완료 기준까지 충족하면 전체 진행표에도 체크한다. 체크는 구현 여부뿐 아니라 해당 동작의 검증까지 마쳤다는 뜻으로 사용한다.

이 문서는 원본 대화 전체를 읽고 최신 논의를 우선해 정리했다. 작업 순서와 검증 항목은 실행하기 쉽게 구체화한 제안이다. 작업 체크박스는 미완료로 시작했으며 이후 결정·검증 결과에 따라 갱신한다. 미정인 값은 해당 단계에서 결정하며, 기능을 구현하기 전에 필요한 결정만 확정한다.

SDK·스토어 정책·지원 버전·계정별 테스트 요건은 작업 시점에 공식 문서와 콘솔에서 다시 확인한다. 이전 조사에서 언급된 버전이나 경쟁 앱의 수치를 현재 사실로 옮기지 않는다.

### 대화에서 제안한 기본안

- 규칙: 사각형 안의 합이 10이면 제거, 사과 1개당 1점, 제거한 빈자리는 유지.
- 기본값: **가로 8칸 × 세로 13칸, 120초**를 출발점으로 실기기에서 검증. 개발 설정으로 바꿀 수 있게 하되, 사용자용 크기·시간 선택 화면은 첫 출시에서 제외한다.
- 첫 버전: 기본 솔로, 짧은 안내, 홈·플레이·일시정지·결과·설정, 로컬 기록, 새 판·같은 판 재도전.
- 로그인 없이 시작하고 오프라인에서도 플레이. 기록은 기기에 저장하며 자체 서버는 두지 않는다.
- 광고는 한 광고망의 전면 광고 하나로 시작. 결과 저장·확인 이후 다음 판으로 넘어갈 때 빈도를 제한해 노출한다.
- 상태 변경은 `GameSession`에 모으고, 입력과 상태 전달에는 R3를 활용한다.
- **UnityHFSM은 최신 논의에 따라 초기 도입을 보류한다.** `GamePhase` enum과 세션 메서드로 시작한다.
- 같은 판 재도전은 연습으로 구분하고, 서로 다른 크기·시간·규칙의 기록을 섞지 않는다.

### 첫 출시에서 보류할 것

실시간 멀티플레이, 계정·클라우드 저장, 온라인 랭킹, 일일도전, 전체 리플레이 화면, 되돌리기·힌트, 콤보 배점, 자동 섞기, 시간 연장, 재화·스킨·상점, 보상형 광고·광고 제거 결제, 여러 광고망의 미디에이션, 자체 운영 대시보드, 범용 게임 프레임워크는 후속 검토 대상으로 둔다.

## 2. 게임 규칙과 데이터 구현

**목적:** Unity 화면이나 입력 장치 없이도 게임 판정을 확인할 수 있게 한다.

- [x] 보드 데이터와 규칙 설정을 Unity 오브젝트에 의존하지 않는 C#으로 표현한다.
- [x] 크기·제한 시간은 불변 설정으로 보관하고 목표 합·점수 정책·규칙 버전을 명시한다. 보드는 입력 배열을 복사해 소유한다.
- [x] 초기 보드 생성과 난수 사용 위치를 한곳으로 모은다.
- [x] 두 셀 좌표를 사각형으로 정규화하고 영역의 합과 유효한 사과 수를 계산한다.
- [x] 합이 10인 선택만 제거하고 제거 개수에 해당하는 점수 변화량을 반환한다. 빈칸의 위치는 유지하며 총점 누적은 3단계 세션에서 담당한다.
- [x] 남은 보드의 가능한 선택 유무를 검사한다. 시작 직후·제거 후 검사하는 세션 호출 흐름은 3단계에서 연결한다.
- [x] 초기 보드 숫자와 규칙을 다시 넣어 같은 판을 시작하고 같은 행동 순서로 같은 결과를 재현한다.
- [x] 합 10/미달/초과, 빈칸 포함·빈칸만 선택, 역방향·경계 선택, 반복 제거, 가능한 수 없음에 대한 규칙 테스트를 통과시킨다.

### 2단계 구현·검증 기록 — 2026-10-07

| 파일 | 역할 |
| --- | --- |
| [GameRules.cs](../Assets/Scripts/Core/GameRules.cs) | 기본 8×13·120초, 목표 합 10·사과당 1점·규칙 버전 1, 불변 설정 및 설정값 검증 |
| [CellRectangle.cs](../Assets/Scripts/Core/CellRectangle.cs) | 역방향 드래그를 포함한 두 셀 좌표 정규화. 양끝 셀 포함 |
| [SelectionSummary.cs](../Assets/Scripts/Core/SelectionSummary.cs) | 선택 합·사과 수·제거 가능 여부·획득 점수 |
| [GameBoard.cs](../Assets/Scripts/Core/GameBoard.cs) | 생성, 행 우선 보드, 조회·복사, 선택 미리보기·제거, 가능한 수 탐색 |
| [GameBoardTests.cs](../Assets/Tests/EditMode/GameBoardTests.cs) | 생성 조건·판정·점수·빈칸·좌표·재현·탐색 검증 |

- `Squapple.Core`는 `noEngineReferences` 어셈블리로 Unity 엔진 의존성을 차단했다.
- 숫자 생성은 마지막 두 칸을 보정해 각 칸 1~9와 전체 합의 10 배수 조건을 만족한다. 최소 두 칸이 필요하며 1×1 설정은 거부한다. 전체 제거 가능성이나 원작과 같은 난수 분포를 보장하지 않는다.
- 빈칸은 `0`이다. 보드 밖으로 벗어난 사각형은 선택 전체를 거부하고 보드·점수를 변경하지 않는다.
- 규칙 설정은 불변이며 입력·출력 숫자 배열은 복사한다. 외부 배열 수정으로 보드가 바뀌지 않는다.
- 시드는 같은 런타임 내 재현에 사용한다. 런타임·버전이 달라도 같은 판을 복원하려면 초기 숫자 배열과 규칙을 저장한다.
- **NUnit 테스트 35개 통과**: 5종 크기·256개 시드의 생성 보드 1,280개, 빈칸을 포함한 보드 300개의 독립 탐색 대조, 고정 사례의 경계·재현·불변성 확인 포함.
- 실행은 설치된 Unity NUnit을 사용해 동일 테스트 소스를 별도 .NET 10 실행기로 검증했다. 로컬 결과는 `.utmp/core-tests/results.xml`에 있다. Unity가 Core·Tests 어셈블리를 생성한 것도 확인했으며, Unity Test Runner 자체에서의 테스트 실행과 모바일 빌드는 이번 검증에 포함하지 않는다.
- Unity에서는 Test Runner의 EditMode에 있는 `Squapple.Core.Tests.GameBoardTests`를 실행할 수 있다. 총점·시간·진행 단계·R3 전달·화면 연결은 다음 단계다.

리플레이를 위한 최소 경계는 `초기 보드 + 규칙/버전 + 확정된 선택 좌표·경과 시간`이다. 매 프레임 터치 좌표 저장이나 전체 리플레이 기능까지 이 단계에서 만들 필요는 없다.

**완료 기준:** 동일한 초기 보드와 동일한 확정 입력 순서로 보드·점수 결과를 재현할 수 있다.

## 3. 세션과 스트림 연결

**목적:** 상태 소유권과 변경 순서를 분명하게 유지한다.

권장 흐름: **터치·버튼·시간 입력 → 세션 요청 → 규칙 검사·상태 확정 → 상태/이벤트 전달 → 화면·연출**.

- [ ] `GameSession`이 현재 보드·점수·남은 시간·진행 단계를 소유하도록 한다.
- [ ] `GamePhase`는 `Ready / Playing / Paused / Finished` 수준으로 시작한다.
- [ ] `Start / Pause / Resume / Finish`와 선택 처리 메서드에서 전환 가능 여부를 판단한다.
- [ ] 외부에서는 변경을 요청하고, 세션 데이터를 직접 수정하지 않게 한다.
- [ ] 사과 제거·점수 증가·종료 여부를 한 번의 처리로 확정한 뒤 외부에 알린다.
- [ ] R3로 전달하는 현재 상태와 일회성 이벤트를 구분한다. 화면 재진입 시 현재 점수는 표시하되 지난 효과음은 재생하지 않는다.
- [ ] 드래그 미리보기와 확정된 보드 상태를 분리한다. 드래그마다 보드 전체를 복제하거나 모든 셀을 스트림으로 만들지 않는다.
- [ ] 남은 시간은 정의한 경과 시간 기준으로 계산한다. 알림 횟수나 프레임 수를 시간 자체로 취급하지 않는다.
- [ ] 일시정지 중 선택·시간 진행 금지, 종료 후 점수 변경 금지, 종료 중복 처리 방지, 시간 종료 경계 동작을 검증한다.

필수 작업의 순서는 직접 호출이나 명시적인 비동기 흐름으로 표현한다. 저장 완료와 광고 노출 순서를 서로 독립적인 구독자의 실행 순서에 맡기지 않는다.

**완료 기준:** 선택 요청 하나로 판정부터 화면 갱신까지 연결되며 구독 순서가 게임 결과를 바꾸지 않는다.

## 4. 세로형 모바일 플레이 완성

**목적:** 첫 사용자가 규칙을 이해하고 편하게 한 판을 마치게 한다.

- [ ] 홈 → 시작 → 플레이 → 결과 → 새 판 흐름과 일시정지·설정 진입을 연결한다.
- [ ] 한두 문장의 규칙 안내와 짧은 예시를 제공한다.
- [ ] 터치를 보드 좌표로 변환하고 드래그 시작·수정·해제·취소를 구현한다.
- [ ] 선택 사각형과 현재 합을 표시하고 손가락에 가려져도 상태를 파악할 수 있는 배치를 확인한다.
- [ ] 보드 밖 이동·화면 가장자리·두 번째 손가락·UI 위 터치·앱 전환으로 끊긴 드래그를 처리한다.
- [ ] Canvas Scaler·앵커와 하나의 Safe Area 처리 방식으로 노치·홈 바·다양한 화면 비율을 대응한다.
- [ ] 작은 화면에서 숫자 크기·칸 간격·버튼 터치 영역을 확인하고 필요하면 개발 설정의 기본 보드 크기를 조정한다.
- [ ] 성공·실패 선택에 즉시 피드백을 주고 제거 연출·효과음이 숫자나 다음 입력을 방해하지 않게 한다.
- [ ] 소리와 진동 설정을 제공한다. 세밀한 햅틱 에셋은 기본 기능으로 부족한지 확인한 뒤 검토한다.
- [ ] 막힘 안내, 남은 시간, 이번 점수·최고 기록·신기록 여부를 명확하게 표시한다.
- [ ] Android 뒤로 가기, 진행 중 재시작 확인, 결과에서 다시 하기 동작을 정리한다.

**완료 기준:** Android·iPhone에서 처음 보는 사용자가 안내를 이해하고 한 판을 마친 뒤 다시 시작할 수 있다. 시뮬레이터 확인에 더해 실제 손가락 조작을 검증한다.

## 5. 중단·복귀와 수명 처리

**목적:** 이전 판의 작업이나 중단된 입력이 다음 판에 영향을 주지 않게 한다.

- [ ] 앱 전환·화면 잠금·포커스 변경 시 타이머·입력·소리를 정한 정책대로 정지한다.
- [ ] 진행 중 드래그를 취소하고 복귀 시 사용자가 이해할 수 있는 재개 상태로 돌아온다.
- [ ] 수동 일시정지·앱 중단·광고 진입이 겹쳐도 원치 않게 자동 재개되지 않게 한다.
- [ ] 앱·화면·한 라운드의 수명을 구분하고 각 구독·타이머·UniTask·트윈의 종료 시점을 정한다.
- [ ] 재시작 시 이전 판의 타이머·늦은 콜백·비동기 작업을 취소하거나 무효화한다.
- [ ] 연출 취소가 확정된 점수·보드를 되돌리지 않도록 한다.
- [ ] 여러 번의 빠른 재시작, 앱 전환, 잠금·복귀를 반복해 중복 처리와 입력 잠김이 없는지 확인한다.
- [ ] 프로세스 종료 후 재실행이 0단계의 정책과 일치하는지 확인한다.

VContainer를 사용해도 게임 화면의 수명과 한 판의 수명은 다를 수 있다. 한 판이 끝났다는 이유만으로 모든 비동기 작업이 자동 취소된다고 가정하지 않는다.

**완료 기준:** 반복 재시작·중단·복귀 후에도 타이머는 하나만 동작하고 이전 판이 새 판의 상태를 바꾸지 않는다.

## 6. 저장·기록·재도전

**목적:** 짧은 플레이가 기록과 다음 도전으로 자연스럽게 이어지게 한다.

- [ ] 로컬 최고 기록, 소리·진동 설정, 안내 확인 여부를 저장한다.
- [ ] 단순 설정은 PlayerPrefs 등 최소 수단으로 시작하고, 구조화된 기록에 필요한 저장 방식만 추가한다.
- [ ] 저장 데이터 버전과 업데이트 후 기존 데이터를 읽는 방식을 정한다.
- [ ] 보드 크기·제한 시간·규칙 버전이 다른 기록은 별도 조건으로 관리한다.
- [ ] 결과에서 새 보드 시작과 같은 보드 재도전을 구분해 제공한다.
- [ ] 같은 보드 재도전에는 원본 보드·당시 설정을 사용하고 연습 기록으로 구분한다.
- [ ] 결과를 먼저 확정·저장한 다음 결과 확인과 광고·다음 판 흐름으로 연결한다.
- [ ] 앱 재실행·오프라인·업데이트 설치 후 기록 유지와 같은 판 재현을 검증한다.

**완료 기준:** 저장된 기록·설정이 재실행 후 유지되고, 다른 조건이나 연습 기록이 일반 최고 기록과 섞이지 않는다.

## 7. 광고와 동의 처리

**목적:** 무료·광고 운영을 경험하면서도 한 판의 흐름을 지킨다.

대화의 우선 검토안은 **Google Mobile Ads Unity Plugin + UMP, 전면 광고 하나**다. 실제 도입 버전의 지원 환경·동의 처리 절차는 연동 시 재확인한다.

- [ ] 광고망 하나와 광고 형식 하나를 확정하고 SDK·네이티브 의존성을 양쪽 플랫폼에 연결한다.
- [ ] 개발·QA에서는 테스트 광고 또는 테스트 기기 설정을 사용한다.
- [ ] 결과 확인 후 다음 판으로 넘어갈 때만 광고 기회를 둔다. 플레이 중이거나 막 시작된 판에는 노출하지 않는다.
- [ ] 첫 판에는 광고를 노출하지 않고 이후 판수·시간 간격 제한값을 정한다.
- [ ] 광고가 준비되지 않았거나 로딩·노출에 실패하면 기다리게 하지 않고 진행한다.
- [ ] 다음 판 시작 뒤 도착한 광고 응답을 무효화하고 광고를 중복 노출하지 않게 한다.
- [ ] 광고 전후의 소리·입력·화면·세션 상태를 복구한다. 외부 앱으로 이동했다 돌아오는 경우도 포함한다.
- [ ] 출시 국가·대상 연령·선택한 SDK에 맞는 동의 필요 여부 확인, 동의 화면, 개인정보 선택 변경 경로를 구성한다.
- [ ] 동의 상태에 따른 광고 요청 가능 여부를 처리하고, 거부·오류·오프라인에서도 기본 플레이가 가능한지 확인한다.
- [ ] iOS ATT 적용 여부를 실제 추적·데이터 사용 방식에 따라 확인하고 필요한 경우에 맞게 구현한다.
- [ ] 성공·닫기·실패·광고 없음·네트워크 끊김·앱 전환·늦은 콜백 경로를 양쪽 실기기에서 검증한다.

**완료 기준:** 광고와 동의 처리에 실패해도 게임은 시작·종료·재시작할 수 있고, 저장된 결과가 손실되지 않는다.

## 8. 오류·사용 반응 관측

**목적:** 출시 후 무엇이 불편한지 확인할 최소한의 근거를 남긴다.

- [ ] 충돌·오류 확인 도구를 연결한다. 대화의 후보는 Firebase Crashlytics와 최소 Analytics다.
- [ ] 첫 실행→첫 판 시작, 판 종료→다음 판 시작, 같은 판 재도전, 광고 후 다음 판 진입을 구분할 최소 이벤트를 정한다.
- [ ] 다음 날 재방문과 광고 실패·충돌을 서비스의 기본 대시보드에서 확인할 수 있게 한다.
- [ ] 필요한 매개변수만 기록하고 수집 항목·수집 조건을 9단계의 개인정보 표에 반영한다.
- [ ] 테스트 빌드에서 오류 보고·심볼 처리와 이벤트 전달을 확인하고 출시 데이터와 구분한다.
- [ ] 빠른 재시작·광고 콜백에서 동일한 종료·광고 이벤트가 중복 집계되지 않는지 확인한다.
- [ ] 통계 서버 연결 실패가 시작·저장·재시작을 막지 않는지 확인한다.

**완료 기준:** 첫 판 진입, 반복 플레이, 재방문, 광고 이후 이탈 여부와 기술 문제를 확인할 수 있다. 표본이 적을 때는 수치를 고정된 합격선으로 취급하지 않고 직접 관찰·피드백과 함께 판단한다.

## 9. 스토어·운영 자료 준비

**목적:** 실제 앱과 일치하는 등록 자료, 문의 경로, 배포 정보를 준비한다.

- [ ] 사각사과·Squapple의 기존 사용 여부와 이름·로고 권리를 확인하고 최종 표기를 정한다.
- [ ] 앱 아이콘, 실제 플레이 스크린샷, 짧은 소개·상세 설명, 필요한 언어별 문구를 준비한다.
- [ ] 세로형 조작감·가독성·빠른 재도전을 소개한다. 리플레이나 기록 비교 자체를 독점적인 기능처럼 설명하지 않는다.
- [ ] 문의 이메일, 지원 페이지, 개인정보처리방침의 접근 가능한 URL을 준비하고 앱·스토어에 연결한다.
- [ ] 광고·통계·충돌 SDK를 포함한 데이터 수집·전송·사용 목적·동의 조건을 정리한다.
- [ ] Google Play Data safety와 App Store 개인정보 표시를 실제 SDK 설정·앱 동작에 맞춰 작성한다.
- [ ] 광고 포함 여부, 연령 등급, 출시 국가, 대상 사용자 관련 등록 항목을 확인한다.
- [ ] 이미지·폰트·음원·오픈소스·유료 에셋의 라이선스와 필요한 고지를 정리한다.
- [ ] 제출 시점의 Android 대상 API·네이티브 라이브러리 요건, Apple SDK·Xcode·개인정보 관련 제출 요건을 확인한다.
- [ ] 계정별 사전 테스트·심사·프로덕션 접근 절차를 일정에 반영한다.
- [ ] 출시 버전·빌드 번호, 심사 설명, 테스트 방법, 변경 사항과 복구 가능한 소스·서명 정보를 준비한다.

**완료 기준:** 광고·데이터·연령·기능 설명이 실제 빌드와 일치하고 문의·정책 링크에 접근할 수 있다.

## 10. 실기기·배포 경로 검증

**목적:** 개발 환경 밖에서 설치·플레이·업데이트가 정상인지 확인한다.

- [ ] 작은 화면·큰 화면·노치·홈 바가 있는 기기와 비교적 낮은 성능의 Android, 지원 범위의 iPhone에서 점검한다.
- [ ] 출시 기본 보드·시간으로 가독성과 판정을 확인한다. 개발 설정을 바꿨다면 변경값도 확인하며 내부 설정의 유효성 경계는 규칙 테스트로 검증한다.
- [ ] 아래 회귀 시나리오를 출시 후보 빌드에서 모두 수행한다.
- [ ] 연속 플레이 중 프레임 저하·메모리 증가·발열·배터리 소모·앱 용량을 확인하고 목표치를 기록한다.
- [ ] Google Play 테스트 트랙과 TestFlight 등 실제 배포 경로로 설치·업데이트를 확인한다.
- [ ] 외부 테스터가 별도 설명 없이 시작·종료·재도전할 수 있는지 관찰하고 막히는 부분을 수정한다.
- [ ] 수정 후 영향받는 항목을 다시 확인하고 출시 후보 버전·기기·OS·결과를 기록한다.

| 점검 | 기대 결과 |
| --- | --- |
| 첫 설치·첫 실행 | 안내 후 로그인 없이 게임 진입 |
| 합 10 선택·실패 선택·역방향 드래그 | 표시 영역과 판정이 일치하고 점수는 한 번만 반영 |
| 제한시간 종료 순간 선택 | 미리 정한 순서대로 처리되고 종료가 중복되지 않음 |
| 가능한 조합 없음 | 지연 없이 안내하고 결과·재시작으로 연결 |

| 동의 거부·변경·동의 화면 오류 | 정의한 광고 요청 정책을 지키고 기본 게임 이용 가능 |
| 강제 종료·재실행 | 기록·설정 유지, 진행 중 판은 정한 복원 정책 적용 |
| 기존 버전 위에 업데이트 | 저장 데이터 유지, 이전 형식 처리 정상 |

**완료 기준:** 진행 불가·기록 손실·판정 오류·잘못된 광고 노출이 해결됐고 양쪽 배포 경로를 통과한 후보 빌드가 있다.

## 11. 양쪽 출시와 첫 수정 업데이트

**목적:** 배포로 끝내지 않고 운영·수정까지 한 사이클을 경험한다.

- [ ] 최종 빌드의 광고 ID·환경·버전·서명·스토어 정보를 확인하고 양쪽 심사에 제출한다.
- [ ] 심사 피드백이 있으면 실제 원인을 수정하고 필요한 점검 후 다시 제출한다.
- [ ] 출시 후 스토어에서 직접 설치해 플레이·기록·광고·문의 링크를 확인한다.
- [ ] 충돌·광고 실패·재시작 막힘을 우선 확인하고 사용자 문의와 리뷰를 함께 기록한다.
- [ ] 첫 판 시작·다시 하기·같은 판 재도전·재방문·광고 후 흐름을 확인한다.
- [ ] 다음 수정 범위를 실제 오류·불편·관측 결과를 근거로 작게 정한다.
- [ ] 저장 데이터 호환성과 변경된 흐름을 확인하고 양쪽에 수정 업데이트를 배포한다.
- [ ] 출시·심사·광고·테스트에서 배운 점을 다음 게임용 절차 메모로 남긴다.

**완료 기준:** Android·iOS에서 안정적으로 서비스되고, 실제 사용 근거를 반영한 첫 수정 업데이트까지 배포했다.

## 12. 후속 실험과 공통화 판단

**목적:** 사용 근거가 있는 기능과 반복 사용이 확인된 공통 부분만 늘린다.

### 제품 확장 순서

- [ ] 같은 판 재도전이 실제로 사용되는지 확인하고 반복 플레이의 불편부터 개선한다.
- [ ] 수요가 있으면 보드 코드·결과 공유로 비동기 친구 도전을 작게 실험한다.
- [ ] 같은 보드·같은 규칙의 비교가 성립하도록 공유 데이터와 기록 조건을 정한다.
- [ ] 풀이 복기의 수요가 확인되면 확정 행동 기록을 활용한 최소 리플레이·분석을 검토한다.
- [ ] 일일도전·온라인 기록·계정은 운영 필요가 생긴 뒤 검토한다.
- [ ] 실시간 멀티는 형태와 수요를 먼저 정하고 서버 판정·연결 끊김·재시작·부정행위 대응을 별도로 설계한다.

OshiZi의 경쟁→비교→복기→재도전 흐름은 참고 자료다. 그 전체 기능을 첫 출시 범위로 옮기지 않는다. [기존 OshiZi 조사 문서](../../make10/docs/research/2026-10-07-oshizi-apple-game.md)는 형제 프로젝트 `make10`에 보관돼 있다.

### 다음 게임에서 공통화할 후보

- [ ] 광고·동의·빈도·실패 처리, 설정·저장, 안전 영역, 중단·복귀, 진단 이벤트 중 실제 재사용 가능한 부분을 가져가 본다.
- [ ] 빌드·서명·SDK 점검표·실기기 테스트·스토어 자료 양식도 함께 재사용한다.
- [ ] 두 번째 게임에서 반복 사용이 확인된 코드만 공용 패키지로 분리하고 버전을 고정한다.
- [ ] 게임별 규칙·보드·점수 구조를 억지로 공통화하지 않는다.
- [ ] 필요가 확인된 경우에만 Feel, Essential Kit, Easy Save, Localization, Notifications, 광고 미디에이션을 다시 비교한다.

**완료 기준:** 다음 기능과 공통화 대상에 실제 사용 또는 재사용 근거가 있고 첫 게임 출시를 위한 불필요한 선행 작업이 되지 않는다.
